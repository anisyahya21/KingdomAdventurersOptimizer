# Original Python optimizer objective, version 3

This specification is transcribed from `project/KA-Website/tools/recovery/strategy_optimizer.py` (`lane_record`, `lane_key`, `lane_qualifies`, `pareto_frontier`, `elite_lanes`, `choose_parent`, `_select_parents`, `accumulate`, `chest_count`, and `potential_chests`). It describes the existing Python implementation; it does not add the later requested boss-arrival/interruption/remaining-store objective.

## Evidence and eligibility

Each candidate is aggregated within `(encounterId, defeatCount)`; runs across different encounter or defeat-count contexts are not pooled. `n`, wins, losses, censored, resource sum, earned count/max, potential max, setup-progress maxima and progress-run count are accumulated from run records. Win reliability is the lower bound of the two-sided 95% Wilson interval (`z=1.96`, successes=wins, trials=n; empty sample gives `[0,1]`). `meanResources=resourceSum/n` when `n>0` and the sum exists; a missing resource measure is treated as zero only in ranking/dominance keys.

The earned outcome is a *victory reward*, not queued callbacks: censored/verdict-unknown is unknown; a resolved loss is zero by the loss gate; a win uses `rewardOutcome.awardedChests`, else `pendingChests`, else `prizeCallbacks`, else unknown. `earnedCount` increases only for resolved wins with a known chest count, including a reported zero. `potentialMax` uses `rewardOutcome.pendingChests`, falling back to `prizeCallbacks`, for either verdict; missing stays unknown. Thus queued rewards on a defeat are not earned rewards.

Eligibility: earned and efficiency require non-null `earnedMax` and `earnedCount>0`; potential requires non-null `potentialMax` and `potentialMax-(earnedMax or 0)>=10`; setup requires `progressRuns>0`. The 10-chest threshold is `POTENTIAL_FOLLOW_UP_MIN_CHESTS`. Historic records with no telemetry do not enter setup.

## Lane sort and pool

All tuples sort descending lexicographically; exact ties retain input order (Python's stable sort). Each lane keeps four records per encounter/defeat group (`LANE_POOL=4`). Missing numeric values in keys are normalized exactly as code: `earnedMax or 0`, `potentialMax or 0`, Wilson lower bound or zero, missing `meanResources` to zero, and missing/non-numeric setup fields to zero.

* earned: `(earnedMax, WilsonLower, -meanResources, n)`.
* potential: `(potentialMax-earnedMax, potentialMax, WilsonLower, -meanResources, n)`.
* setup: `(postDeathPrizes, commandsReleasedAfterDeathTargetingBoss, storedCommandsTargetingBossAtDeath, maxSimultaneousCommandsTargetingBoss, commandsTargetingBossReleased, storedTargetHoldersPeak, maxSimultaneousStoredCommands, potentialMax, earnedMax)`.
* efficiency: first take the Pareto frontier on `(earnedMax, -meanResources)`: another record dominates iff it has at least as many earned chests and no more resources, with one strict. Then sort by `(earnedMax, -meanResources, WilsonLower, n)`.

The other recorded progress fields and earliest event ticks are evidence/UI data, but are not in the setup lane's ordering tuple. A missing resource mean is treated as zero for Pareto comparison in the current code.

## Parent draw helper (and active production path)

The standalone `choose_parent` helper behaves as follows: every fifth zero-based proposal (`proposal_number % 5 == 4`) draws uniformly from the population and labels the source `exploration`. Otherwise it tries lanes in the fixed order earned, potential, setup, efficiency, rotated so lane `proposal_number % 4` is first; each lane pool is filtered to members still in the population. It chooses from the first nonempty pool. If every lane pool is empty, it chooses from the population and labels it `exploration`. One RNG `choice` call is made per helper call. The parity oracle replaces that random call with `drawIndex % len(choicePool)`; this fixture schedule is deterministic and is not a claim about cross-language PRNG equivalence.

The production caller is `spawn_children`; neither `choose_parent` nor an `_select_parents` function has a call site. Module default is `LEARNER_MODE='branching'`; ordinary top-up requests four children. `spawn_children` builds per-defeat-group lanes and concatenates their top-four members by lane into an encounter-wide source pool. Its default source list is `earned,potential,setup,efficiency,region,exploration,mean`; source for an attempt rotates by `(proposal_number+attempt) % len(kinds)`. Parent choice within a source is weighted by `0.5 + lineage productivity`, where productivity is `(improved descendants+1)/(children+2)`. Lane improvement means the child qualifies and either the parent did not or the child's lane key is strictly higher. The normal turn reserves `int(count*0.35)` local probes and `max(1,count//4)` fresh synthetic roots before general branching; root starts from population and severs parent lineage. Under sustained starvation, a distinct reseed source list (`elite,historical,region,root`) and explicit stat-exploration/restart probabilities apply.

The per-encounter feedback also adapts mutation selection. Operator weight is `max(0.35, 1 + 2*improved*(improved+1)/(attempts+4))`; every attempted operator is bumped, and improved is credited if any lane improves. Numeric-stat scale weights are `max(0.35, 1+2*improved-0.15*max(0,attempts-improved))`; scales are 1.05, 1.15, 1.4, 2, 3, .95, .7, .5 plus a jump weight. Stat anchors move to values that improved a lane. A local probe's contextual direction evidence is grouped by encounter, strategy region, unit, stat, and percent change; paired same-seed outcomes take precedence when available. This is the implemented choice logic, but the current Python feedback path does not increment `improved` for `stat:<name>` or for a numeric scale entry; it records attempts/planned values only. Consequently those per-stat and per-scale success weights do not learn from normal child outcomes in the current runtime (the scale weights mostly decay toward the 0.35 floor as attempts accrue, and the jump weight stays at its base unless a prior state already contains improved counts). General operation weights and stat anchors do receive lane-improvement feedback. So the original optimizer does have an experience-based prediction-like loop, but it is not accurately described as currently learning which stat scales succeed, and it is not a general function that predicts an arbitrary whole strategy's battle result.

The parity fixture's `choose_parent` proposals test a defined helper only, not the active parent scheduler. In a fixed Synthetic DPS / fixed-skills / only-ATK-SPD-LCK experiment, disable fresh roots and non-stat operations by explicit test configuration; preserve the exact lane ranking and measured feedback formulas where applicable. Such a controlled adaptation must be labeled as constrained original learner, not full production scheduler parity. Reseed and local behavior also need their active conditions preserved or intentionally disabled with the reason recorded.

## Saved-evidence and objective limits

Native result `progressMetrics` maps to the Python setup fields in `PROGRESS_MAX_FIELDS`; observed numeric values aggregate by per-candidate maxima, and `progressRuns` counts rows carrying the progress object. `bossDeathTick` and `firstPostDeathCommandReleaseTick` are minimum-tick evidence, not setup sort keys. The requested objective additions—interruption, stored attacks at boss arrival, and remaining stores at boss death—must be separately mapped from actual journal/native telemetry before they can be ranked. Missing telemetry remains unknown; do not substitute a synthetic zero or infer it from a related counter. Victory is the dispatch trigger for queued rewards, so queued-at-victory and certified awarded/retained outcomes must remain distinct fields.

Raw journals and source manifests should be hash-bound in any migration. Aggregate only valid, unique result IDs and preserve method, seed, encounter, candidate, and source-journal provenance. This spec/oracle does not mutate or migrate any optimizer state.
